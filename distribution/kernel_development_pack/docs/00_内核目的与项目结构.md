# 00. 内核目的与项目结构

本分发包使用 VibeFlow 0.10.0。Python 代码必须从所属分层包导入；根包不重导出业务对象，两个 Target 及其 Application closure 不得互相依赖。

VibeFlow 通过明确的程序结构约束，让项目长期保持低耦合、可审计和可维护。

它适合人机协同开发，尤其适合让 LLM 参与长期项目开发。LLM 很容易把功能越写越大，或者在出问题时用补丁覆盖问题。这个内核要求所有业务能力都拆成小型、可审计的 node，并用 JSONC 配置组织成标准流程图。普通 node 保持纯函数；真实 IO 只能出现在内核按 `flow_kind` / `external` 派生并审计的 effect scope 中。只要 node 或配置违反规则，运行前健康检查会拒绝执行并给出原因。

## 使用者需要开发什么

通常只需要开发这些目录：

```text
python_project/
  nodes/            # Python 业务 node
  base_lib/         # Python 纯 helper
  plugins/          # Python Plugin
  configs/          # Python workflow 和 nodeset
  registry.py       # Python 资源注册
javascript_project/
  nodes/            # JS/TS node
  base_lib/         # JS/TS 纯 helper
  plugins/          # JS/TS Plugin
  host_extensions/  # JS/TS 宿主生命周期扩展
  manifests/        # 静态 descriptor
  configs/          # JS workflow 和 nodeset
  web/              # 可选 Web 入口
```

每个 root 用 `project_target: "python" | "javascript"` 选择一种 Target。Python
资源由 `registry.py` 登记并在 workflow 中按 ID 使用。JS/TS AOT 资源由
`vibeflow_project.jsonc.descriptors` 登记；Plugin 与 Host Extension 分别由 workflow
顶层 `plugins`、`host_extensions` 按 ID 选择。planned 资源只进入架构审查，
不解析源码、不执行、不打包。一个 workspace 可以包含两个 root，但单次 workflow
和 nodeset import 不跨 Target。

内核建议作为单文件归档放在：

```text
kernel/
  vibeflow-kernel.zip
  MANIFEST.sha256
  README.md
  docs/
  tools/
    mermaid-renderer/
  THIRD_PARTY_NOTICES.md
```

业务开发时不需要解包它，也不应修改 `kernel/` 下随内核分发的文档、工具配置和许可说明。公开对象按职责导入：

- `vibeflow.core`：通用 contract 与流程模型。
- `vibeflow.targets.python.project`：Python Node、Registry、base_lib 与 Plugin。
- `vibeflow.targets.python.quality`：Python 实现与 workflow 健康检查。
- `vibeflow.targets.python.runtime`：Python Runtime 与执行选项。
- `vibeflow.targets.javascript.frontend|quality|build`：JavaScript Target 的绑定、审计与构建。
- `vibeflow.tooling.project`：两个 Target 共享的 JSONC、workspace 与路径加载。
- `vibeflow.tooling.application.python|javascript`：分别编排自己的 Target；Python 边界同时包含运行和架构表现。

例如：

```python
from vibeflow.core import DataProvider, DataRequirement
from vibeflow.targets.python.project import NodeContract, NodeInfo, NodeRegistry
from vibeflow.targets.python.quality import HealthFinding
from vibeflow.targets.python.runtime import RuntimeOptions
from vibeflow.tooling.application.python import run_checked
```

如果需要 SVG 图输出，分发包还会包含：

```text
kernel/tools/mermaid-renderer/
```

启动脚本建议放在项目根目录：

```text
run.py
```

## 标准工作流

开始前先判定任务类型，不要把新建项目和修改已有项目混成同一套流程。

### 新建项目（greenfield）

1. 把需求先表达为粗粒度的 planned flow，必要时用独立 planned nodeset 逐层细化。
2. 在真实 root 的 `configs/*.jsonc` 中声明 planned 调用点的 `id`、`display_name`、`description`、`flow_kind` 和数据契约；只有复用既有 implemented 类型时才在审核前写 `type_used`。
3. 用显式 `pipeline.edges` 组织待审核 flow，必要时将大块拆成独立 planned nodeset；此阶段不实现 Python node。
4. 用 `python run.py review --config ... --output ...` 更新登记架构文档、完成正式校验并生成 canonical expanded SVG，供人类审核。
5. 只有人类在后续消息中明确批准后，才为 planned 部分实现 `NODE_INFO`、`CONTRACT`、`run_pure(self, inputs, params)` 并在 `python_project/registry.py` 注册，最后再做 runtime probe。

### 修改已有项目（existing）

1. 先读取所属 root 登记的 `ARCHITECTURE.jsonc`，再沿其 source 定位真实 workflow config、nodeset 和 registry。
2. 修改前列出`复用 / 修改 / 删除 / 新增`清单，写明 source path、node/edge id、现有职责和计划变化。清单未列出的 id、edge、hook 和调用层级默认保持。
3. 在登记的同一个 workflow 及其导入的 nodeset 上原位修改；只把真正待审核的新增或变更部分标为 `planned`。
4. 不得为了审核新建平行 config，也不得用概念图或手写 Mermaid/SVG 替代真实 config 审核。
5. 使用同一条 `run.py review` 流程审核；如果用户要求“审核后再实现”，本次 review 成功也不是批准，必须等待后续明确消息。

Runtime 默认审计流程而不是数据内容：node 间可以按引用传递 tensor、model、optimizer、batch 等 Python 对象；报告和 trace 只记录 key、事件、summary 和失败位置，不保存真实对象内容。

## 分发包里不要改什么

这些文件由构建脚本生成，业务开发者和 AI 不应修改：

- `kernel/vibeflow-kernel.zip`
- `kernel/MANIFEST.sha256`
- `kernel/README.md`
- `kernel/docs/`
- `kernel/tools/mermaid-renderer/package.json`
- `kernel/tools/mermaid-renderer/package-lock.json`
- `kernel/THIRD_PARTY_NOTICES.md`
- `run.py`

`run.py` 会在启动时校验这些内核和启动器文件。如果有人把内核源码重新解包到 `kernel/vibeflow/`，校验会把它当作 unexpected 文件并拒绝继续运行。根目录的 `README.md`、`AGENTS.md` 以及项目自己的说明文档是给使用者定制项目流程用的，不属于内核完整性校验范围，可以按项目需要修改。

分发包不内置 `.gitignore`，Git 忽略策略由项目自行决定。常见建议包括忽略 `kernel/tools/mermaid-renderer/node_modules/`、`runs/`、`reports/`、`__pycache__/` 和 `*.pyc`。

## 常用命令

在复制了模板的项目根目录运行：

```powershell
python run.py validate --config python_project/configs/main.jsonc
python run.py review --config python_project/configs/main.jsonc --output reports/graph.expanded.svg
python run.py run --config python_project/configs/main.jsonc --run-root runs
python run.py delegate-cli --config python_project/configs/main.jsonc -- --input data.yaml --verbose
python run.py mermaid --config python_project/configs/main.jsonc --output reports/graph.mmd
python run.py ascii --config python_project/configs/main.jsonc --output reports/graph.txt
python run.py svg --config python_project/configs/main.jsonc --output reports/graph.svg
python run.py svg --config python_project/configs/main.jsonc --expand-nodesets --output reports/graph.expanded.svg
python run.py inspect-config --config python_project/configs/main.jsonc
python run.py quality --path python_project
```

`validate`、`review` 和 `quality` 检查 VibeFlow 图与架构边界，不判断 JS workflow
是否支持 Browser 或 Node。JavaScript 每次通过 `build --target browser|node` 选择
本次构建实现；完整类型、lint、平台 API 与业务测试由项目工具负责。

首次使用 `svg` 命令前，需要在 `kernel/tools/mermaid-renderer/` 执行 `npm install`。

不要求系统预装 Google Chrome。正常执行 `npm install` 后，Puppeteer 会安装并使用自己的浏览器缓存；如果该缓存不可用，VibeFlow 会再尝试非 snap 的系统 Chrome/Chromium。`/snap/bin/chromium` 会被跳过，因为它在 Puppeteer/mermaid-cli 下常见 profile lock 启动失败。

正式架构审核使用 `python run.py review`，它会生成 canonical expanded SVG 并在发布前检查其结构。单独的 `svg` 命令仍可用于诊断或图形导出。`python run.py mermaid --expand-nodesets --output reports/graph.expanded.mmd` 只生成 Mermaid 源码调试文件；Mermaid CLI/mmdc 是 VibeFlow 内部渲染实现，不是公开审核入口。

`validate` 和 `run` 都会执行强制健康检查。`run` 在检查失败时会拒绝运行，并把报告写入运行目录。

需要把 workflow 当成普通业务命令行程序时，使用 CLI 让渡模式 / `delegate-cli`。它把业务参数作为 `cli.argv` 传入图，从唯一 `cli.exit_code` 输出取 `0..255` 退出码，并保留真实 stdin/stdout/stderr。首个 `--` 可用来明确分隔 core 参数与业务参数，也可省略。VibeFlow 自身诊断写入当次 run 目录的 `vibeflow.log`，不污染业务标准流。`delegate-cli` 不替代通用执行命令 `run`，也不改变正式架构审核命令 `review`。

## 关键变化

- 旧 `boundary` 模型已移除。
- 旧 `pipeline.loops` / pipeline 或 edge 级 `max_iterations` / edge `max_executions` 已移除；训练循环使用一等 loop node 的 `loop.max_iterations`。
- `flow_kind=io` 对应 `effect_scope=terminal`，可使用真实标准流、`print` / `input` / `argparse`。
- `flow_kind=document` / `data_store` 对应 `effect_scope=python_io`，可使用文件、环境、网络、数据库、subprocess 和终端。
- 普通 implemented node 和 planned `python_stub` 对应 `effect_scope=none`。
- 任意 `flow_kind` 只要 `NodeInfo.external=True`，即以最高优先级使用 `effect_scope=trusted`；plugin 也是 `trusted`。它们仍须遵守契约、拓扑、输出和 trace。
- 图形 `flow_kind=terminal` 仍是 `effect_scope=none`，不等于权限档位 `terminal`。effectful / external node 的 examples 只做结构检查，不执行。
- 训练/批处理类 side task 可显式使用 `async: "detached"` 或 `async: "result_key"`，但 runtime 不自动合并异步 context。
