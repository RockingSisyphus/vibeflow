# Python / JavaScript AOT 暖调用开销复现与方案分析

2026-10-20，基线为 1.1.4（e2f6281）。初次复现只增加沙盒和记录；随后按用户选择的方案二修复 Python AOT，见文末落实记录。优化后来随 81aaa30 提交；本文中的原始样本和数字仍是当时的历史证据，不代表当前 ABI 的复测。

## 范围与方法

本机 Linux，Python 3.13.13、Node v24.18.0。Python 使用交接 ZIP 原有监工 Core Bundle，实际执行代码来自当前仓库 src；加载一次后，每次创建独立 Runtime，执行真实 settings.get，使用合成身份与临时空数据库，不读取原任务状态。五次暖调用的 profile 仅用于调用次数；四种模式各八次的计时关闭 profiler，顺序交错，所有返回设置相同。临时方法替换在 finally 中恢复，未修改 SDK 文件。

JS 通过公开 SDK 和正式 build_project_aot 构建 1、32、138 个串行加一节点，加上边界为 2、33、139 种节点类型。每个产物一次导入、预热后各执行 100 次，改变输入并核对结果。它不是监工业务的 JS 移植，不据此计算跨语言性能倍率。函数计数使用另一份诊断副本；空钩子对照也使用独立副本，与原包交错计时，原产物保持原样。

复现入口：[Python](../../sandbox/python/aot_preparation/README.md)、[JavaScript](../../sandbox/javascript/aot_preparation/README.md)。原始样本、profile 次数、首次脚本失败及后续结果保存在仓库旁 `VibeFlow-evidence/aot-preparation-20261020`，临时包、库和依赖均在使用结束后清理。

## Python：重复固定准备已复现

同一 139 节点 Bundle 的五次暖调用：`_descriptor` / `decode_resource` 各 695 次，`Plugin.bindings` 695 次，`_registry` 与模块扫描各五次，`bind_python_workflow` 十次。路径是 `create_runtime → _registry → _descriptor`，以及首次绑定节点实例时 `registry.get → resolve → Plugin.bindings`。运行实例内的 NodeRegistry 已缓存实现类型，但下次新建 Runtime 又从头开始。

| 进程内实验 | create_runtime 中位 ms | run 中位 ms | 完整调用中位 ms |
| --- | ---: | ---: | ---: |
| 原实现 | 27.48 | 28.75 | 55.61 |
| 只复用固定 Descriptor | 13.93 | 29.05 | 43.13 |
| 只复用 Plugin 绑定索引 | 27.33 | 11.92 | 39.17 |
| 两者 | 12.80 | 11.27 | 24.39 |

各列独立取中位数，阶段中位数之和不必等于完整调用中位数。两者合用的本机完整调用中位数降低约 56.1%。原始 Bundle 加载约 0.440 秒，未计入暖调用。缓存实验只验证单 Bundle 下固定资料复用的效果，不是生产缓存实现，也未验证跨 Bundle、并发或所有生命周期。

本次没有运行 Windows VM 的原调度／恢复完整组，不能把本机机制复现当作原 120 秒超时已重现或已修复。模块路径扫描承担跨项目导入隔离，不能为追求本表数字直接禁用。

## JS：没有同类重复注册，存在独立的空钩子工作

所有规模的原产物中，静态执行工厂 `createStaticWorkflowSync` 只在模块导入时调用一次；其后的五次调用工厂计数为零，`prepareWorkflowInvocation` 为五次。节点描述为模块级常量，执行直接引用已绑定函数；生成物中未出现 SDK definePlugin 函数。不是每次调用重新遍历资源、构建节点注册表的路线。

但 `invokeRuntimeHookSync/Async` 在检查是否有钩子接收者之前就构造 `runtimePluginSummary`。没有运行插件的 139 类型案例，五次调用仍构造 1420 次摘要，递归 deepFreeze 函数进入 11290 次；后者包含原始值和递归访问，不代表 11290 个不同固定 Descriptor。

| JS 节点类型数 | 原包中位 ms | 空运行插件时跳过摘要的副本，中位 ms |
| --- | ---: | ---: |
| 2 | 0.466 | 0.458 |
| 33 | 0.689 | 0.690 |
| 139 | 1.463 | 1.384 |

该空工作确实存在，但单批耗时收益较小，小案例没有稳定改善。它不支持“JS 与 Python 有同一个瓶颈”的结论。本轮实测为同步 Node AOT，未把源码共用的异步／浏览器路径宣称为已实测。

## 方案比较与建议

| 路线 | 行为与成本 | 判断 |
| --- | --- | --- |
| 仅缓存 Descriptor | 修改最少，保留每次重新生成插件绑定表 | 不完整，实测仍约 43 ms |
| Bundle 准备一次固定资料，运行期只创建独立实例 | 复用现有 AOT loader、NodeRegistry 和执行器；调整固定资料准备的位置，不改 ABI、SDK bindings 返回语义或业务调用接口 | 推荐，已测到主要收益，职责最清楚 |
| 重写为 JS 式完整静态 Python 调度器 | 可能进一步降低装配成本，但需重做插件、循环、trace、取消等现有语义，与共享执行器形成维护负担 | 本轮证据不足以支持这项成本 |

推荐边界：Bundle 负责本包的描述转换、路径定位、固定实现绑定索引；Runtime 仍拥有自己的注册表、Node 对象、参数、Capability、插件生命周期实例与清理状态。Plugin 定义可以延续当前惰性加载时机，在首次取得定义时一次读取其绑定表，由本 Bundle 保存；无需修改 SDK 的公开返回行为，也不提前调用运行插件工厂。

正式实现不照搬诊断中的 id(record) 缓存和类方法替换。直接使用按 Bundle 生命周期持有的准备结果，避免全局 LRU、失效策略、全局锁和多层缓存。固定 Descriptor 可以在 Bundle 装载时一次转换；注册表和可变执行帧继续每次新建，不复用完整 ExecutionPlan 或 Runtime。这样修复的是固定工作放错生命周期的位置，而非增加另一套执行流程。

JS 可独立将钩子摘要改为“发现第一个有效回调时才构造一次”，同步和异步调度保持同一规则。这比不断添加特殊快路径更直接，同时覆盖零插件与插件未实现某个钩子的情形；本轮副本仅验证了零插件同步情形。

运行回收自引用与模块扫描是并列事项，不与上述 56% 混为同一原因。若处理自引用，应先检查工厂是否只需捕获 run_dir 等值，避免引入弱引用管理层；本轮未重新验证 GC 诊断，也未据此解释 Windows 退出延迟。

正式修复仍需跨 Bundle 的 A→B→A 同名模块切换、独立参数及 Node 实例、并发、插件生命周期与异常清理，以及 JS 有无回调、同步／异步和失败钩子检查；最后用作者新包执行原 Windows 完整组。无需为这些改动建立新的发布资格框架。

复现脚本的早期失败分别是遗漏 Schema、遗漏 terminal 入口、诊断副本文件名未区分 .js 和 .mjs，以及多计算节点误用重复 provider key；均已修正并保留原日志，不计作产品失败。通过后仅执行对应沙盒与项目质检，未重复完整测试门禁。

## 方案二落实与验证

`PythonBundle` 在装载时准备一次节点及运行插件 Descriptor，并转换节点实现路径、成员路径和来源信息。首次使用插件时，将其固定绑定表保存在本 Bundle 中；节点解析和运行插件工厂查找共用该索引。删除了每次创建注册表时的插件加载闭包及重复 JSON key 序列化。Plugin 的公开 bindings() 行为不变，插件加载与生命周期工厂调用仍保持惰性。

每次 create_runtime 仍创建独立 NodeRegistry、执行帧和 Node 实例；运行插件实例仍按每次 run 创建和清理。未缓存完整 ExecutionPlan、Runtime、Capability 或业务对象，也没有增加全局缓存、锁、ABI 版本或另一套执行器。原跨项目模块扫描保留。JS 的空钩子建议尚未混入本次 Python 修复。

相关回归 108 项通过，覆盖首次／预热后并发、A→B→A 同名模块切换、参数覆盖、独立 Node 与插件实例、清理失败、取消、trace、Loop／Nodeset、安装包及源码移除后的部署。第一批为 66 通过、1 失败：新增隔离测试漏声明 support.py 的 implementation_files，被构建正确拒绝；补齐测试项目后复验通过，原日志保留。

原 139 节点交接实包使用当前 src 执行，五次暖调用的 Descriptor 解码和 Plugin.bindings 完整表构造均为零次；每次仍正常建立独立注册表和执行计划。非 profiler 计时的生产公开路径（normal）中位耗时为 29.54 ms，create_runtime / run 各列中位数为 13.32 / 16.27 ms。前次原实现的 55.61 ms 与本次属于分批测量，不作为严格 A/B 倍率；诊断缓存分组的更低数字也不当作生产性能。

修复记录在仓库旁 `VibeFlow-evidence/aot-preparation-fix-20261020`。本次没有重复完整测试门禁，没有运行 Windows 原完整组，不能宣布原 120 秒整组超时已解决。已有 AOT 产物携带内嵌框架，使用者需要重新构建产物才能带入修复；没有直接修改交接包或监工项目。
