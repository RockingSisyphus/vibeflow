# 目录职责整改

## 目标与已确认约束

- archive 只保存被替换的历史发行包，dist 只保存最新正式发行物。
- distribution 保存构建器、模板、提示词、最小项目和用户文档的唯一原稿。
- docs 保存开发说明、决策、审核结论及证据索引。
- sandbox 只按 Python / JavaScript 两个目标保存真实使用案例；用户已确认直接加载工作区 src 可以保留。
- tests 保存非沙盒功能、代码和实现回归；quality、references、src、tools 保持各自既有职责。
- 现有正式 0.15.2 包不因目录调整被提升为开发中的 0.17.0；核心产品行为不变。
- 原始证据、退休测试备份和历史发布物不得因整理丢失。

## 实施顺序与验收

1. 核对文件用途、跨目录引用、Git 状态和待清理路径的活动使用情况。
2. 在仓库旁的 VibeFlow-evidence/directory-remediation-20261009 保存完整历史材料与迁移清单。文档保留可检索原路径、大小和 SHA-256；历史材料中的路径按当时现场理解，不改写原始证据内容。
3. 将用户文档原稿迁入 distribution/docs，修改 profile 配置、构建器和开发导航；发行包内部的 kernel/docs 路径保持不变。
4. 将内部回归项目移入 tests/fixtures；跨目标回归 runner 同样属于 tests。真实多文件资源项目分别归入 sandbox/python 和 sandbox/javascript。原始生成结果和运行目录移出沙盒。
5. 将最新正式 ZIP 归入 dist，审核 ZIP 归入外部证据。调整构建器：新 ZIP 默认进入 dist，替换的正式包进入 archive，保持发布失败可回滚。
6. 清理确认未活动的 dist 工作目录，保留可复现输入及观察；生成的依赖、缓存和源码副本使用结束即清理。补充有限的目录职责质检及相关行为测试。
7. 定向验证文档链接、质检、构建和迁移入口，通过后固定版本运行一次完整仓库测试批次。失败安全时尽量跑完整批，集中修复后先定向验证，再决定必要的全量复验。
8. 核对最终目录、证据可恢复性、正式发行物与 Git 差异，记录实际验收及清理结果。本任务不自动推送或发布。

## 执行中的成本、目标与路线复核

主要成本是测试案例分类、硬编码路径修正以及双目标完整验证；文件搬迁本身成本较低。大型证据需一次读取和校验，剩余验证耗时以现有完整批次实际运行确认，不虚构精确工时。

关键假设：用户文档迁移能够保持发行包内部布局；内部回归可以迁移而不减少覆盖；旧生成产物不是运行输入；正式 ZIP 可与现有正式目录对应；历史证据能在仓库外完整保存而仍可检索。

在首次文档打包通过、测试迁移入口通过、完整批次结束及交付前，结合实践证据复核剩余工作量、验证代价、维护负担和这些假设。复用实际验证，不增加固定审批或测试轮询。若同类路径修补不断出现，检查是否应统一根目录发现，而不是持续补偿错误。

常规等价实现、明确错误和已有偏好足以决定的调整自主完成。若证据显示目标或核心机制需要改变，或小幅调整目标可产生实质不同且更有价值的结果，按 critical-fork 先做低成本核查，再用可独立阅读的中文说明解释同一使用场景下各路线的因果、结果、成本和未知，及时征求用户判断。不能因本计划已获授权而静默削减测试或舍弃更好路线。

确需用户介入时，说明准备好后按 codex-task-alert 的资格与发送规则提醒；只暂停依赖决定的部分，继续保留选项的已授权独立工作。可低成本保留的有价值选项记录具体讨论节点，最迟在路线定型前讨论。得到决定后更新本计划、验收依据与必要的决策记录。

## 验收节点复核记录

文档装配与迁移入口均已通过。首批全量约 25.4 分钟，仅发现三项文档路径/索引问题；修正后完整 pytest 为 4,221 passed，质量自身测试 53 passed，双 profile 交付复验通过。

复核确认产品核心和独立场景输入没有变化，后续复验集中在有改动的文档、质量与发行范围。其他首批结果通过 1,484 个输入文件的双向逐字节比较沿用；没有缩减案例、恢复已退役分析器或更改用户确认的源码加载方式。完整记录见 [整改结果](directory-remediation-results-20261009.md)。
