# Rule 机制统一重构：目标、决策与验收

本文记录已确认的行为，作为长期实施和维护的判断依据。最终完整验收已通过，实际成绩及验证边界见 [实施结果](rule-mechanism-refactor-results.md)。

## 已确认的目标

静态声明提供默认，动态 Config 表达当前对象的完整选择。两者使用同一 Rule、Ruleset、依赖图、执行器和诊断协议；仅选择来源不同。Node 类型和内置/所选 Plugin 的 Workflow Ruleset 提供静态默认，Workflow、Nodeset、Node 调用允许动态选择。使用位置决定资料接口，不能因静态或动态来源改变接口。

| 配置 | 最终行为 |
| --- | --- |
| 未填写 | Node 使用类型默认；根 Workflow 使用静态 Workflow 默认；子 Nodeset 继承父层有效选择 |
| 明确非空列表 | 完整替代对应默认或继承列表 |
| 明确 `[]` | 取消对应层级选择，保留其他层级约束与原生错误 |

Node 调用替换仅作用于该调用。例如类型默认检查十个 `t`，某次调用选择检查十个 `d`，该调用只执行 `d`，同类型其他调用仍使用 `t`。首次延迟绑定、编译、运行和报告都遵守相同选择，不允许加载阶段恢复默认。

Node 规则只取得当前声明、当前调用参数、自己的实现和继承实现，以及实际引用的 helper 闭包。同文件其他 Node 的源码、AST、符号、归属、其他调用、全量 Catalog、全局注册表不通过公开接口暴露。源码位置保留真实文件和行列。这是可信 Rule 的接口契约，不建设文件系统安全沙箱。

Workflow/Nodeset 规则取得当前命令实际加载的图、调用关系、相关声明、源码和语言资料，可以检查连接、契约、分支、汇合、可达性、跨层路径及整体数量。公开上下文明确区分当前图、可查询的背景、负责范围和子图接管边界。“全局”限于当前命令的相关闭包，不扫描项目孤立文件。

图级约束与 Node 局部约束共同生效：Workflow B 与 Node A 得到 B+A，但 B 不作为 Node 规则重复执行。Node `[]` 仅取消局部规则。Nodeset 显式 C 替代父层 B 对内部的图级约束，内部局部规则仍保留；B 继续检查该 Nodeset 调用在父图中的外部连接和契约。Nodeset `[]` 同样建立接管边界。即使显式列表与父层相同，也建立新边界。重复调用按实际路径分别解析，循环体按静态结构检查一次，不随迭代次数重复。

## 范围、协作与复用

- `current_graph` 为缺省范围：子 Nodeset 是父图中的有限调用边界，子任务负责内部；父子执行相同规则时，检查对象互不重叠。
- `effective_subtree` 在有效范围入口执行一次，遍历范围内各张图；继承子图不重复调度；显式子选择阻止内部遍历。
- 每个完整 Ruleset 依赖计划只有一种范围；嵌套未声明范围继承外层，明确冲突时报组合错误。Node 不接受整体范围 Ruleset。
- 原有 Rule `scope="source"/"call"` 表示对源码或调用的依赖，独立于图范围。source 检查不得读取当前调用参数或其他调用列表；有调用依赖的检查使用 call。
- 同范围 Rule 通过 Records 和显式 `requires/bindings` 共享分析结果；不按执行先后猜测依赖，不隐式传递跨范围 Records。
- 首先消除重复范围调度，再复用等价计算。相同资源 ID 不是复用依据；实现、参数、阶段、输入 Records、资料和负责范围变化必须正确失效。缓存只存在于当前命令。
- 报告说明默认/动态/继承来源、被替代列表、负责路径与边界、实际执行与复用，以及全部受影响位置。调用政策和指标以完整路径贯通运行及 Architecture；类型摘要不能覆盖调用事实。

内置 `vibeflow.workflow` 保留综合能力，明确使用整体范围。分析、连接、汇合、Nodeset、重复逻辑、planned、Target review 和汇总由可见的依赖计划组合，保留 `planned_events`、`workflow_review`，不在一个 handler 内偷偷递归调用其他规则。

## 为什么这样设计

整表替代使用户能预测最终规则；使用位置限制资料依赖，使局部实现与图关系检查各司其职；读取背景和负责范围分离，使跨层分析与子图接管同时成立；明确范围后才复用，避免凭重复诊断推测是否已检查；同范围 Records 共享分析，避免新增结果分发系统。发生歧义时，以这些用户可观察行为裁决，不以复用旧代码为由恢复默认、公开全局 Node 资料或补回隐藏递归。

## 目录与责任

`core/rules/selection/static` 和 `dynamic` 仅读取不同选择来源；`selection/resolve.py` 统一默认、继承和替代；`planning.py` 统一调用层级、范围和边界；`graph.py` 处理 Ruleset 组合和 Records 依赖；`execution.py` 保持单一执行器。Targets 提供语言事实与实现绑定，不重建选择语义。静态 Workflow 默认使用既有 Ruleset 的 `workflow_default` 标记，无第二注册系统或独立全局定义文件。

完整迁移删除旧默认注入、类型回退执行、重复私有缓存和隐藏递归，更新 SDK、Schema、示例、仓库 Plugin、测试与文档。JavaScript Rule ABI 升为 `vibeflow.rule.v2`，外部插件须按新资料边界迁移。

## 验收依据

覆盖缺省/替代/空列表、首次绑定和运行、同文件多 Node/helper、三级嵌套/重复调用/循环、本层和整体计数、B/C/A 外部与内部边界、Records 依赖/失败/范围冲突、缓存失效和诊断归属、各阶段资料可用性、未调用声明与双 Target 一致性。测试使用真实 Python、TypeScript Rule 与 CLI。

实施前工作区状态及差异保存于本次外部验证目录，不修改其他已有工作。最终在包含当前源码和未提交改动的隔离副本执行 `python tools/verify_project.py --full`，避免全量脚本清理原工作区。整批测试期间不修改被测代码，结束后集中修复并定向复验。记录次数和耗时，调用减少不能直接证明性能提升。不自动提交或推送。

## 执行中的成本、目标与路线复核

主要成本是符号级源码隔离、首次延迟绑定、调用政策贯通、综合规则拆分、双 Target 和发行验证。复用既有分析器，不增加第二执行状态机。关键假设是符号及实际引用能提供局部闭包、综合检查可拆成同范围 Records、公共规划可替代分散选择。

复核节点：首个配置到运行的完整原型；嵌套/整体范围与协作验证；双 Target 及内置迁移完成；出现连续补偿与路线定型前。每次用新证据检查剩余工作、验证成本、维护负担和目标假设。明确实现错误自主修复；若证据要求改变用户可见目标，先提供完整中文说明再征求取舍，只暂停依赖决定的部分。实际验收通过后按任务通知 skill 发送一次完成提醒。

### 实施复核记录

配置到首次运行的原型验证了缺省、替代和空列表能够分别生效，延迟绑定不恢复被替代的类型规则。三级图、重复调用、显式空边界和 Records 协作验证了范围规划可由 Core 承担，两个 Target 保留各自语言事实，不增加另一套执行器。

源码边界是主要维护成本。Python 使用既有符号与引用资料构造文本和 AST 的一致投影；TypeScript 使用真实编译器符号解析继承实现及 helper。祖先 Node 的声明元数据不能随继承实现泄漏。新增实际 Target 测试同时检查文本、AST、查询接口和原生语法错误，未增加文件系统沙箱。

第一轮完整批次跑完全部 17 步，暴露 49 项 pytest 失败及沙箱、规则矩阵、发行检查问题。集中修复了路径政策、Nodeset 声明分析、编译失败的诊断保留、失败 Records 的可用性判断及源码审查覆盖；迁移了读取全局配置的 Node 测试和按整文件计量的 Node 边界案例。文件范围约定改为图级示例规则，局部检查继续保留；没有通过清空规则或降低阈值解决失败。

双 Target 迁移后的定向证据包含 207 项适配场景、10 项缓存场景、真实 TypeScript 行数/字节边界、继承与同文件源码隔离，以及领域示例和文档发行。配置变动、不同 Records 和重复调用各自保持诊断归属。剩余成本集中于完整批次、浏览器/渲染及两种发行配置的验收，第一轮约 40 分钟，不能用定向测试取代。公共选择、范围与依赖仍分属既有几个小模块，未补入隐藏执行路径；此时没有证据要求改变已确认目标。

第二轮完整批次跑完全部 17 步，pytest 4,247 项、双 Target 场景、性能、适配、wheel 与双发行配置通过。规则矩阵暴露三个父图误认子图 helper 为孤立源码的问题：归属查询须使用命令背景，实际检查仍限于负责范围。修复后的 20 项组合场景全部匹配。隔离副本的文档链接依赖缺失单独补齐，最终副本必须包含所有被引用的工作区资产和外部证据。

路线定型前的只读复核还发现：空选择不能阻止未调用 Nodeset 的原生编译；JavaScript 源码调用收集须复用 Core 的完整路径规划；根 Workflow 预览须展示选择来源；同一 Rule 的不同参数引用不能按 ID 合并；共享 Nodeset 分析须保留全部受影响调用位置。对应修复仍使用现有规划、执行与报告模块，没有另建状态机或结果分发机制。剩余工作是修复版的完整验收与证据归档；第二轮约 41 分钟，验证成本已经有实际记录，尚无旧版性能对照。目标和资料边界均保持已确认约定。

第三轮全部 17 步完成，规则基线 1,219 项、补充矩阵 680 项、性能与 10 个缓存探针、适配、浏览器、wheel 和双发行配置均通过；pytest 为 4,252 通过及一项文档索引缺项失败。索引补齐属于文档修正，不改变规则行为。工作区同时有独立数学沙箱迁移，原改动保留，最终副本还须覆盖迁移后的入口与配置。第三轮约 46 分钟；不把已通过的规则检查与未通过的整批结论混为一谈，最终验证继续使用固定副本。

最终复核：固定副本与原工作区的 1,946 个文件一致，17 步完整验收通过，4,253 项 pytest、双 Target 实际运行、规则矩阵、缓存、浏览器、wheel 和双发行配置均通过。一次临时目录用户配额中断单独记为未完成，释放本任务旧副本的重复历史与缓存后，相关测试和完整批次通过，没有改动规则行为。公共选择、范围、依赖与执行的职责保持原划分，源码局部投影仍是两 Target 的主要维护点；不增加跨范围分发或第二状态机。关键假设获得现有验收支持，没有需要缩减目标的证据，也没有旧版性能对照可支持提速结论。
