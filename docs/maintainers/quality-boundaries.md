# 架构质检的阻断边界

本次统一 Python 与 JavaScript 规则时，按 `code-rigor-boundaries` 的四项准入条件审查了触碰的检查。这里的“通过”只指该检查满足当前动作的边界，不代表工作流已经运行成功。

| 检查阻止的动作 | 用户要求或必要边界 | 不检查的实际损害 | 四项准入条件 | 处置 |
|---|---|---|---|---|
| `quality-check` 以错误状态退出 | 用户明确要求架构质检的 `FAIL` 和退出码 1 | 检查命令无法如实报告超限；执行构建时不会读取其历史结果 | 这是测量命令本身的结果，不是其他命令的运行准入；直接、局部且无资格状态 | 保留错误结果；警告只给 `CONCERNS` 和退出码 0 |
| `validate`、`review`、`build` 拒绝当前图的 nodeset 深度超限及当前已注册实现的硬规则违规 | 用户明确要求这些直接处理对象遵守已有图／实现规则 | 图或实现可在违反明确架构约束时被接受，后续执行不会自然指出该约束 | ① 用户要求；② 当前输入；③ 违反明确约束且自然执行不会报告；④ 复用局部 Core 规则。四项满足 | 保留原有命令作用范围；宽度仍为非阻断警告 |
| 非法 `runtime.nodeset_max_depth`／`javascript.nodeset_max_depth` 或质量策略字段使当前配置解析失败 | 当前命令必须获得确定的正整数限制和可用策略 | 布尔、零或非整数会令比较失去定义；下游普通错误不能准确指出字段 | ① 输入 schema 必需；② 当前字段；③ 否则无法可靠比较并定位字段；④ 局部解析。四项满足 | 保留最小 schema 校验，报告具体字段 |
| 在 `build`／`run`／`validate`／`review` 前扫描所有未注册源码或读取既往质检报告 | 没有用户要求这些命令做项目级预检 | 不检查不会妨碍这些命令处理其直接输入 | ①②③不满足；还会扩大作用范围 | 不加入；全项目源码只由 `quality-check` 扫描 |
| SHA、manifest、receipt、全量 dry-run、预测性资源与跨配置锁 | 没有当前动作所需的外部边界 | 不检查时由实际操作返回真实错误 | ①②③不满足；可能引入第二套控制面 | 不加入 |

验证证据分别记录为 Core／语言事实测试、隔离 CLI 沙箱和真实项目只读质检；这些证据不替代工作流真实执行。
