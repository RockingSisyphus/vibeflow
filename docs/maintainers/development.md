# 内核开发与验证

本文说明内核维护的修改边界、验证入口和文档装配；业务项目接口见[使用者文档](../README.md#使用者开发)。

## 修改边界

- Core 保持语言无关；
- Block Compiler 不加载项目文件或语言实现；
- Python 与 JavaScript Target 彼此隔离；
- Tooling 承担文件系统与 CLI 编排；
- 公共行为同时更新 Python、JavaScript presenter、文档和测试。

仓库可能包含未提交修改。实施变更时在现有工作树上合并，避免重置或覆盖无关内容。

## 验证入口与边界

安装 Python 测试依赖：`python -m pip install -e '.[test]'`。统一入口为：

```bash
python tools/run_tests.py --workers 4 -- tests/e2e/test_execution.py
python tools/run_tests.py -- --collect-only
python tools/verify_project.py --full --workers 4
```

`run_tests.py` 只运行选定的端到端场景；`verify_project.py` 依次运行仓库质量、隔离副本的语法编译、同一个端到端批次、最终质量与清理预览。`--full` 将 wheel/sdist 和两个发行 profile 的安装、解压、搬移运行也纳入该批次；省略它仅排除 delivery 场景。完整批次不再追加另一套 sandbox 总包。

默认最多 12 个 worker，可用 `--workers` 或 `VIBEFLOW_TEST_WORKERS` 调整，命令行优先。按文件分配 worker，文件内共享工程的修改、构建、运行、恢复顺序保持串行。测试调度不改变业务 `max_concurrency`。

入口固定本仓 `src`，关闭用户站点和第三方 pytest 插件自动加载。pytest 先在仓库目录解析原生命令参数，公开配置钩子再将已解析的测试目标固定为绝对路径，并在导入测试模块前切换至隔离工作目录；`-k`、`-m` 等选项值不被当作路径改写。并行调度进程留在调用目录启动 worker，实际收集与执行发生在各 worker 的隔离目录。临时目录、日志、依赖及构建产物均位于仓库外。省略 `--scratch` 自动清理；显式提供仓库外目录则由调用者负责清理和保留所需结果。工具链按 `tests/e2e/runtime/package-lock.json` 一次准备，集合查看和纯 Python 场景不安装 Node 依赖；仅需 Node 的场景不下载浏览器。已有环境可通过 `VIBEFLOW_TEST_TOOLCHAIN_ROOT`、`VIBEFLOW_BROWSER_RUNTIME_ROOT` 复用；系统 Chrome 可用 `PUPPETEER_EXECUTABLE_PATH` 指定。缺少必需运行环境报错，不当作通过或自动跳过。

所有维护的测试位于 `tests/e2e`，真实示例源码保存在 `sandbox`。测试从正常 SDK 声明、CLI、构建所得产物、应用宿主或页面控件进入，只断言正常结果、诊断、导出、日志及自然 DOM。共享辅助只驱动命令、文件、隔离环境和浏览器，不实现解析器、编译器或规则。不得构造内部 IR/RuleContext、替换模块/布局、调用页面业务函数、窥探缓存/AST/内部对象身份或统计内部调用次数。

同政策的源码案例通过独立路径和位置组合在真实项目内运行；拒绝案例匹配目标 code、严重级别和适用位置，同时保留合法及误报对照。会中断加载的错误独立执行。计算与跨语言预期独立给定。业务 Node 自己发出的工作开始、清理完成日志可验证并发和补位；活对象由正常应用传入并检查返回业务对象，不检查框架对象身份。

性能场景记录固定工程的完整构建与运行时间、正常子进程资源占用，以及编辑、恢复、跨工程隔离后的实际结果。数据供同环境比较，不设任意跨机器速度阈值，也不声称端到端能证明内部缓存或依赖方向。后者仍由静态检查和代码审查负责。

逐域入口、判据与验证边界见[测试覆盖](../../sandbox/TEST_COVERAGE.md)。Python 的运行输入检查与 JavaScript JSON Schema 校验按各自现行公开行为验证，不把 JS 的值域校验能力宣称为 Python 已具备。

## 批次与执行复核

日常只运行受影响功能域及必要的错误对照。只有涉及执行差异时才扩展源码、Python 三模式、Node/浏览器组合。复用不变工程的正常构建产物与依赖；输入改变则正常重新构建，不增加缓存身份系统。

完整验收前冻结代码、输入和预期。批次中安全且能推进时收齐失败，不边跑边改；结束后集中修复、定向复验，再根据变更影响判断是否重跑完整批次。`verification.json` 记录各阶段状态，`acceptance.xml` 记录场景及性能观察。定向成功不能改写先前失败，也不能代替全量结果。

在首个样板、主要规则矩阵、取消与清理、浏览器/性能、CI 定型及完整验收节点，按新证据复核剩余工作量、验证成本、维护负担和目标假设。重点检查：正常入口是否能表达目标、组合诊断是否仍能定位、自然输出是否足以判定、跨环境覆盖是否真实。不得为省时静默删覆盖或增加内部探针。若证据要求改变用户结果或验收范围，先查明事实，再解释同一场景各路线的结果、代价和未知，交由用户判断；常规等价实现自主完成。

Linux CI 使用 Python 3.11、Node 22/24 跑完整入口；Windows 使用 Python 3.11、Node 24 验证宿主、协作、命名入口、编码、SDK、资源及 JS 构建。某一台机器的通过不能代替未运行平台。

仓库自检器独立于产品规则：

```bash
python repo_check/run.py --profile all
python tools/audit_retired_architecture.py
```

前者检查目录、依赖方向、Target 隔离、生成物、文档链接及发行源；后者检查已退役架构引用。用户项目仍通过正常产品质量命令检查。

## 文档维护

- `distribution/docs/user/` 面向业务项目的开发者与 AI，说明如何声明、启用、检查、构建和查看资源；
- `distribution/prompts/` 为 AI 提供任务导航和 profile 协议，链接使用手册中的完整规范；
- `docs/design/` 的系统架构与执行模型解释当前内核，仅保留仍待执行的计划，已完成任务的有效知识并入当前规范；
- `docs/maintainers/` 面向内核开发者，记录修改、验证和发行操作；
- 同一规范在一个位置完整定义，其他文档链接到对应主题；
- 示例按公开 SDK 与实际 schema 编写，加载边界在相关操作处说明；
- 优先描述操作及结果，必要限制准确定位到适用场景。退役计划和报告删除，历史溯源使用 Git。

修改文档后运行文档一致性与可执行示例测试，再按[发行装配](release.md)构建两个包。检查生成 AGENTS 的阅读入口、复制后的链接和公开示例，分别核对内容正确性与包内字节一致性。
