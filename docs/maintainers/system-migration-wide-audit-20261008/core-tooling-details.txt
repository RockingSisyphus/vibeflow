# Core / 通用 Tooling 的多轮迁移残余审计（当前工作树，2026-10-08）

只读范围：`src/vibeflow/core`、`block_compiler`、`builtin`、通用 `tooling/project` 与 `tooling/presentation`，以及 Application 的规则预览、资源查询、Python 展示和 JS review 出口。参照原 R01–R19、S01–S04 与修复记录，但逐项以当前源码判断。HEAD 为 9c443f3，包含大量未提交整改；未运行全量测试、未修改产品与已有文档。历史交叉核对 Git 8926a87、3ff4c0a、e25dd05、e553628、f169429、788a1ab、28ebb58、3ee7396，以及实际解包 0.10.0 / 0.14.2 / 0.15.2。

## 总判定

本层没有证实两个完整旧、新资源/规则系统仍作为正式主入口并行。SDK 贡献、统一 Catalog、RulePlan 执行器是真正的正式链。原固定 quality→内置小图→quality 桥、重复 RuleCatalog、旧静态目录等已删除或移走，不再复报。仍确认 3 处小型旧辅助代码/测试负担；另外 7 类保留边界确实沿用旧词汇、旧表达或算法，但理由和删除条件各不相同。不能把这些保留项加进“迁移未完成缺陷”计数。

## 确认的清理遗漏

### C01：旧资源路径 / import 搜索辅助函数失去全部仓内消费者

- 当前 `tooling/project/resource_helpers.py:10–17` 的 `_resolve_paths`、`:19–37` 的 `_module_search_path` 仍原样在产品包中，`:51` 仍导出两者。
- 历史：8926a87 将它们从旧资源配置模块分拆进此 helper。实际 0.10.0 和 0.14.2 的 `tooling/application/python/project/resources.py:8,121,150,257` 用它们解析 `base_lib.paths`、module 搜索根，并临时改 `sys.path` 导入旧 Registry 资源。0.15.2 仍消费 `_resolve_paths`，但 `_module_search_path` 此时已无真实消费者；当前旧 resources.py 已退役，两个辅助函数均无消费者。
- 当前生产者/消费者：对 src/tests/tools/quality/sandbox 的精确符号检索与 AST 检查，两符号仅见本模块定义和 `__all__`（`tools/run_tests.py` 同名 `_resolve_paths` 为独立函数，不是消费者）。新 SDK 路径是 descriptor_loader→Application plugin_definitions→Target SDK loading/source_paths，与这两函数没有调用边。
- 影响：没有已证实的业务结果差异；仍保留已退出入口的 `sys.path` 修改逻辑与旧路径配置概念，维护者容易误以为旧资源加载器仍需保留。
- 删除边界：只删两函数、相关 sys/contextmanager/Iterator import 及 `__all__` 项；同模块 `_finding` 为 Host/resource diagnostics 活跃消费者，不能删整文件。私有名称仍在 `__all__`，只能证明仓内无用，未知第三方直接导入不等于已证明不存在。

### C02：旧 JS Architecture+SVG 成对发布事务仅被旧单测保护

- 当前 `tooling/application/javascript/cli.py:954–1023` 的 `_publish_review_pair` 保留完整 staging/backup/rollback 两文件事务逻辑。
- 历史：3ff4c0a 正式 `handle_review` 调它同时发布 Architecture 与 SVG；e25dd05（0.12.0）改为先独立写 Architecture、后渲染并发布 SVG，移除了正式调用，但函数保留至今。
- 当前链：`handle_review:451`→`_atomic_write` 写 Architecture；`:475`→`write_review_svg` 写临时 SVG；`:511`→`os.replace` 发布 SVG。src 无 `_publish_review_pair` 调用；唯一仓内消费者为 `tests/tooling/test_javascript_review_publish.py:71–101` 的直接私有函数单测。
- 影响：不会把正式 review 回退到旧事务，但测试仍证明一个生产入口已经不用的承诺；维护者看该函数或测试名易误以为 review 仍保证两文件一起回滚。
- 删除边界：删除此函数及该直接测试，或把该测试改为观察当前 `handle_review` 的已确认行为。不要据此恢复旧成对发布行为；当前 Architecture 先更新本身是 0.12.0 已变更的流程，不是本轮发现的新回归。

### C03：旧单浏览器选择函数只剩三个直接测试调用

- 当前 `tooling/presentation/mermaid.py:398–400` 的 `_find_chromium` 只返回 `_system_browser_candidates()` 首项。
- 历史：早期 SVG renderer 只选一个系统 Chromium；e553628 改为 Puppeteer bundled browser优先，再尝试所有非 Snap 系统候选；同时留下 `_find_chromium` 供旧测试。之后重构搬到 Target-neutral renderer，当前 Python `mermaid/render.py` alias仍把它暴露给旧路径。
- 当前正式链：`render_mermaid_svg:70`→`_puppeteer_launch_options:380–383`→`_system_browser_candidates:386–395`；没有 `_find_chromium` 调用。唯一消费者是 `tests/tooling/strict_mermaid_cli.py:9–51` 三个直接断言。
- 影响：只有少量旧辅助出口/测试债，不是两套 renderer，正式 renderer已使用新候选序列；旧测试可以继续通过而未单独证明候选序列行为。
- 删除边界：只删该函数并把三个测试移到正式 `_puppeteer_launch_options` / `_system_browser_candidates` 观察；现有 bundled / non-Snap fallback 渲染测试仍需保留。公开可用性函数 `is_mermaid_svg_renderer_available` 不在此删除清单。

## 确实保留，但不能当作上述缺陷的内容

### K01：旧 Python 输入合同的 `required=None` 语义

`core/contracts.py:42–52` 自分层重构 8926a87 即明确保留该值；`:258–265` parser仍允许省略。GraphConfig.inputs保存此合同。Python `runtime/support/contract_mixin.py:19–26` 遇到任意一个 None就跳过整个 closed-input ABI检查，连其他required=True及unknown-key检查也跳过。JS AOT `build/project_graph.py:310–318` 在正式入口拒绝None，portable plan validation亦要求bool。这是已明确保留的 Python兼容契约与目标差别，值得告诉用户，不能谎称跨目标完全同义，也不能悄悄删掉变成更严格行为。若将来要求统一合同，应先明确怎样迁移旧workflow的required值，再更新兼容承诺与验收。

### K02：旧 `node.async` 表达仍进入同一调度机制

`core/config/graph.py:179,444–470`→NodeSpec.async_mode→Python Frame / ThreadPoolExecutor；portable `block_compiler/compiler.py:430–450` 将它规范成 schedule/executor，JS事实可用async_executor=event_loop，于是旧result_key进入同一个JS scheduler。`vibeflow.io` 是 receive/send端口节点，按自身completion处理，`:254–258`拒绝同时node.async。不存在旧独立parser或第二scheduler的证据。这是保留表达和原生职责。更名/删除需要迁移JSONC、Runtime与任务语义，而非删除“legacy”字样即可。

### K03：Core合同→WorkflowPlan投影不等于双注册模型

`core.flow.GraphConfig`是规范化工作流合同；`core.compiler.CompiledGraph`是解析后的拓扑/执行事实；portable `WorkflowPlan/BlockPlan`是闭合传输IR，JS binding只补实现，Python native ExecutionPlan持真实callable/实例。它们是编译阶段和语言运行绑定，不是两套资源声明权威。

`block_compiler/compiler.py:729–774` `_legacy_inputs/_legacy_outputs` 实际逐字段投影Core当前合同，并未解析旧格式。公开 `compile_graph_plan` 仍允许supplied pipeline_inputs/outputs，只核内部key/type/cardinality顺序，因此低层自制plan可改required/输出alias；JS根生成器只以 `plan.inputs`为权威（`emission_view.py:286–301`），entry block.inputs不是第二个执行输入入口。正式build不传override；未观察正式配置两份权威冲突。低层覆盖能力与正式build边界应分开说明，若移除这些旧名或参数，须先核公开调用者与AOT测试。

### K04：Python展示旧路径 facade 有真实生产消费者，但全部委托共享实现

四个保留模块：`python/presentation/style.py`（star重导出）、`python/presentation/mermaid/render.py`（sys.modules alias）、`mermaid/review_layout.py`、`mermaid/review_types.py`（逐项重导出）。来自 0.11 / 0.12 共享renderer / SVG composer抽取，当前HEAD本来就已是facade。生产消费者包括 `runner.py:311`、`cli/export.py:23,276`、`cli/review.py:359`、`mermaid/review_svg.py:21,25–27`、`review_fragments.py:12–24`。它们使旧import路径暂时不能直接删，但实现权威只有 `tooling/presentation`，不是两套style、renderer或composer。可先迁移仓内消费者至共享路径，然后决定是否维持外部import兼容；不能把facade当重复算法文件整删。

### K05：旧字段和报告名称被规范为一个模型

- `NodeSpec.name/node_type`（core/flow.py:193–199）只读取id/type_used；`NodesetSpec.name/exports`（:234–240）只读取type_key/provides。原生mainline与workflow算法仍大量读这些alias。它们不保存第二份字段。
- `Finding`是共同模型，`HealthFinding` / `QualityFinding`仅constructor与JSON视图兼容（core/findings.py:1–6,96–180；core/quality/models.py:119起）；SourceQualityReport=QualityReport（models.py:366–369）、WorkflowHealthReport=HealthReport（quality/workflow.py:19）是同类alias。
- `override_child_config` / `values` / Host的 `name/settings`仍在Core scope与Tooling Host parser允许；进入规范字段时按固定优先级选取新名。Host contract仍检查选中descriptor，未获得另一份实施来源。它们是旧格式别名兼容，不是旧资源注册主入口恢复。

删除这类名称需要迁移内部算法/序列化消费者，并明示外部合同变更；仅因老名字仍在不能判定迁移失败。

### K06：旧图/AST/结构判定算法是Rule实现，主题粒度仍明确保留

`builtin/workflow.py:14–44,61–75`调用 `core/quality/workflow_rules` 的flow/join/planned与Core nodesets/duplicates算法，默认综合workflow没有逐topic子图。`builtin/project_quality.py`用 dependencies/duplicates/structure/root_structure算法，但使用正式RulePlan执行、有效params和typed records。旧 public append_flowchart_health、append_join_policy_health、nodeset_quality_findings、duplicate_logic_findings、planned_health_events仍是直达共同纯算法的包装，并由部分native adapters / parity沙箱使用；它们当前不再创建隐藏固定Rule小图。

不是每个诊断都单独可替换、builtin Target callable表不是全部外置SDK文件，这些是已经记录的组合/原生绑定边界。若用户另要求每个细检查都成为可覆盖规则，需新的路线工作，不属于本轮可以宣告缺陷的事项。

### K07：历史命名的结构政策仍活跃，但可配置、不会伪造资源身份

`core/quality/models.py:116` distance_exempt_stems保留 runtime/runner/health/cli/cli_reports/cli_config/cli_node；与f169429相同。`structure_distance.py:37–38,155–157`按module leaf精确匹配跳过距离诊断，任意项目沿用这些名称仍会免检，因而不能说是完全没有效果的死值。`builtin/project_quality.py:74`将其作为有效policy conventions，当前 `docs/design/baseline-rule-inventory-core.md:42,153`明确保留并有runner/custom_runner/entry对照。它是可配置的通用结构规范，不赋Node/BaseLib身份，不是S01复发；若未来目标消除所有名称豁免，应单独修改该policy。

同理 `QualityStructureLimits.allowed_root_code_files` 默认仍含registry.py；JS Target以自己的index.* conventions替换默认。这是保留通用布局政策，而不是自动加载旧Registry文件。

## 排除项及覆盖边界

- schema_resources.py无src静态入边，但公共schema_text读取打包JSON Schema，`tests/fixtures/support/strict_support.py:42`及wheel/schema打包核查依赖它；不能整文件删除。
- descriptor source_bundle.py保存SDK plugin declaration与显式source membership，当前不发现JSONC manifest；decode/rule_decode为贡献传输protocol，不是旧目录发现。
- PluginSelection / plugin_review是生命周期内部metadata；SDK selection入口仍拒绝ID-only旧注册。HostExtensionResource是selection/review projection，合同与rulesets从canonical descriptor取得，没有重新建立实施权威。
- 常规unused import只是局部清理候选，不上升为迁移问题。静态候选另存 `/tmp/vibeflow-wide-core-import-candidates.json`；不能按候选清单删模块。
- 历史旧发布包与冻结证据只读，不把它们计为活动源码，也未发现当前正式链从旧包加载资源。
- 本报告未重跑全量验收，也不证明任意业务或第三方公开API用法正确。真实retained input/async差异由Python/JS代理共同核对；本层没有为获得更高问题数而把有意保留机制误报成缺陷。
