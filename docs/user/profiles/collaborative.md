# 人机协同开发协议

collaborative profile 适合需要人类在实现前审阅架构变化的任务。

1. 阅读已登记 Architecture 并定位真实 source。
2. 列出复用、修改、删除、新增四类变更清单。
3. 修改现有流程时，在其真实 Config 的实际位置标记或新增 planned Node、Nodeset；不得另建审核专用流程代替原位变更。
4. 对受影响的完整工作流运行 `review`，生成正式展开 SVG。
5. 等待人类在后续消息中明确批准。
6. 实现获批内容，更新 Architecture，并运行适用的 validate、quality、build 和工作流执行探针。

机器检查结论与人工批准分别报告。profile 协议不改变 Core、契约、副作用或质量规则。

## 正式审核图与真实流程

- 正式审核图必须由 VibeFlow 支持的 Config 经 `review` 生成，不得手绘、手改生成物，或用局部摘录、概念图、单纯表意的 Config 替代。辅助说明图可以另附，但不能作为正式批准依据。
- 修改已有工作流，应沿已登记 Architecture 的 source 找到真实入口、Nodeset 和调用位置，在那里表达 planned 变更；完整图必须保留未修改部分及真实上下游关系。跨多个工作流时分别生成各自的完整图，不能用独立汇总流程替代。
- Config 是实际构建与执行的来源，必须表达真实输入输出、控制流、依赖及实现位置。planned 可以表示尚未实现的变化，但不能借此把任意示意配置称为可运行架构；包含 planned 的审核状态与已实现、已执行的状态应分别报告。
- 新项目或确需新增独立工作流时，说明现有流程为何不能承载，并明确真实调用方、入口、与已有流程的连接，以及构建和执行路径；在相应真实配置中表达适用的接入关系。不得仅凭新建 Config、登记 Architecture 或“以后会接入生产”认定它已符合正式审核要求。修改现有环节不得以新增独立工作流规避原位审核。
- base_lib、Plugin 或 Host Extension 的变更应追溯到真实资源登记、源码依赖和生产调用方；不能为了在图中展示它而虚构 Node、连线或运行入口。
- `review` / `validate` 通过只代表工具报告的检查通过，不证明配置与生产调用一致，也不代表 planned 已实现或业务已验收。审核材料必须提供上述真实调用依据，人工批准仍遵循前述步骤。
