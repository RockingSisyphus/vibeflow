# VibeFlow 长期工作流、同步执行与宿主扩展改造计划

> 状态：本计划的同步/异步入口、永久 loop、Port 与 Host Extension 已在 JavaScript Target 中落实。0.9 当前 API 以 `js_aot_build.md` 为准。

## 总结

本计划扩展现有工作流语义：

- 扩展 `vibeflow.loop.while`，允许有限、条件停止和明确的永久循环；
- 增加内核级 `vibeflow.io`，让 Python Runtime 与 JS AOT 都能表达外部输入和输出；
- JS AOT 默认生成真正同步的工作流，异步必须由 pipeline 和流程结构显式声明；
- 增加可由 JS AOT 静态检查、打包并管理生命周期的通用 `host_extension`。

VibeFlow 负责忠实表达、静态审计和构建用户声明的程序结构。对于逻辑有效但可能长期占用资源的结构，采用显式配置和非阻断 warning，而不通过隐藏上限或强制退出策略限制用户。

## 一、统一执行模型

### 1. Pipeline 入口模式

在 pipeline 增加公共字段：

```jsonc
{
  "pipeline": {
    "entry_mode": "sync"
  }
}
```

`entry_mode` 取值为：

- `sync`：同步入口，缺省值；
- `async`：显式异步入口。

JS AOT 根据入口模式生成不同的公共 ABI：

```ts
// entry_mode: "sync"
export function runWorkflow(
  inputs: WorkflowInputs,
  options?: WorkflowRunOptions,
): WorkflowOutputs;
```

```ts
// entry_mode: "async"
export async function runWorkflowAsync(
  inputs: WorkflowInputs,
  options?: WorkflowRunOptions,
): Promise<WorkflowOutputs>;
```

要求：

- 不根据节点实现自动把同步工作流升级为异步工作流；
- 模块被 import 时不自动执行工作流或启动宿主扩展；
- 同步入口失败时直接抛出 `VibeFlowWorkflowError`；
- 异步入口失败时通过 Promise reject 同一个错误类型；
- 每次调用仍具有独立的 context、trace、错误、任务和 Capability；
- JS ABI 为 `vibeflow.workflow.v2`，只导出与 `entry_mode` 对应的入口。

### 2. 分开完成方式、调度方式和执行器

通用计划分别记录等待、调度和执行位置：

```text
completion: immediate | suspend
schedule:   inline | deferred | detached
executor:   current | event_loop | thread
```

- `completion` 描述实现被调用后能立即返回，还是需要等待 Promise。
- `schedule` 描述工作是否留在当前流程上，或成为需要显式 join/清理的任务。
- `executor` 只记录实际执行机制，不改变流程图的数据和调度语义。

异步但串行等待的节点使用 `completion: suspend + schedule: inline`。工作流会暂停等待它完成，期间不调度下游节点，因此它不是流程分支。

需要先启动、后续再取得结果的工作使用 `schedule: deferred`，并生成可被后续节点 join 的 `TaskPlan`。不向主流程提供结果的旁路工作使用 `schedule: detached`，但仍归属于本次工作流调用并接受清理和错误处理。

### 3. Python Target 映射

Python Target 使用以下映射：

- 未声明 `async` 的节点映射为 `schedule: inline`；
- `async: result_key` 映射为 `schedule: deferred`；
- `async: detached` 映射为 `schedule: detached`；
- `result_key` 继续作为 deferred TaskPlan 的显式 join key；
- `runtime.run()` 继续阻塞返回，不删除现有线程池行为；
- Python 普通同步 callable 标记为 `completion: immediate`；
- 把同步 callable 放入线程池只改变 executor 和 schedule，不改变 completion。

旧 Python pipeline 缺少 `entry_mode` 时继续按同步公共入口处理。其显式 `result_key` 或 `detached` 节点仍可使用现有线程池；这类配置若构建为 JS，同步目标必须根据 JS 是否具备同步 join 能力进行静态拒绝，不得偷偷改变入口 ABI。

## 二、静态审计

### 1. Node 与 Capability 完成契约

为 JS/TS node implementation 和 Capability operation 增加：

```jsonc
{
  "completion": "immediate"
}
```

TypeScript Compiler API 负责验证声明与源码一致：

- `immediate` 实现不得是 `async function`；
- `immediate` 实现的返回类型不得包含 Promise 或 thenable；
- `suspend` 实现必须返回 Promise，并且只能进入 `entry_mode: async` 的 JS 工作流；
- 同步 JS 工作流中出现 suspend、deferred 或 detached 时构建失败；
- 异步工作流可以包含 immediate 节点、串行 suspend 节点和显式 TaskPlan；
- 不进行同步到异步的自动提升。

Python 自动生成的旧节点描述默认使用 `completion: immediate`。Python 线程池的显式分路继续由节点的 `async` 配置表达。

### 2. Promise 所有权检查

普通 node 只能：

- 立即返回普通值；
- 将 Promise 作为 suspend 节点的返回值交给当前工作流；
- 通过显式 deferred/detached 调度把任务交给 TaskPlan；
- 通过已声明的 Capability 调用外部能力。

以下隐藏后台行为构建失败：

- `fetch(...).then(...)` 后不返回或登记 Promise；
- `void promise`；
- 模块级 Promise 或可变业务任务；
- 在普通 node 中注册长期事件监听器；
- 启动定时器、Worker 或其他后台任务后绕过 TaskPlan；
- 通过 base_lib 隐藏上述行为。

VibeFlow 不增加运行时 Promise/thenable 兜底。无法静态证明满足同步契约的源码不能进入同步构建。

宿主运行时注入且无法检查源码的 Capability 实现属于明确的信任边界。构建清单记录其 ID、operation、声明的 completion 和来源，但 VibeFlow 不在运行时猜测或改写它的行为。

### 3. 首版执行器边界

首版保留：

- Python deferred/detached 使用现有 `thread` executor；
- JS suspend/deferred/detached 使用 `event_loop` executor；
- 普通同步节点使用 `current` executor。

首版不实现 Web Worker。以后可以为 TaskPlan 增加 `worker` executor，而不改变流程图中的 completion、schedule、result_key 或 join 语义。

## 三、通用 Host Extension

### 1. 定位

新增独立于 Python `RuntimePlugin` 的 JS/TS AOT `host_extension` descriptor。Host Extension 用于表达浏览器、Node、WebView 或桌面容器的宿主接线代码，例如：

- 注册和注销宿主事件；
- 维护 Port 队列；
- 提供 Capability implementation；
- 处理中止和宿主生命周期；
- 在宿主要求的同步回调中调用同步工作流。

这些操作不是普通业务节点。Node 负责事件转换、校验、路由、状态计算和副作用顺序；Host Extension 只负责把宿主接口接到 VibeFlow 的公共 ABI 和 Capability 边界。

### 2. Descriptor 与源码 ABI

项目配置用 `descriptors.host_extensions` 登记可用 Host Extension descriptor，
workflow 顶层再用 `host_extensions` 显式选择本流程实际使用的扩展。Descriptor 至少声明：

- 稳定 ID；
- `browser` 或 `node` target；
- JavaScript/TypeScript 源码位置；
- 提供的 Capability 和 operation；
- 外部包依赖；
- 与其他 Host Extension 的显式依赖。

扩展源码统一导出：

```ts
export function createHostExtension(
  context: HostExtensionContext,
): HostExtensionInstance;

interface HostExtensionInstance {
  capabilities?: WorkflowCapabilities;
  start(): void | Promise<void>;
  stop(): void | Promise<void>;
}
```

workflow 使用项支持字符串 ID，或包含 `id`、`status`、`enabled`、
`config/settings`、显示元数据、`targets`、`provides` 和 `dependencies` 的对象。
implemented 项必须解析到登记 descriptor；其配置作为冻结的
`context.config` 传给工厂，而且每个 host 得到独立的深冻结副本。工厂必须
同步返回扩展实例；生命周期方法仍可返回 Promise。planned 项可暂时没有 descriptor 或源码，进入
Architecture JSON 与 Mermaid/SVG 审查，但不参与打包、实例化、生命周期或
Capability 提供。implemented 扩展不能依赖 planned 扩展。

每次 `createWorkflowHost()` 创建新的 extension instance，不允许用模块级可变对象共享调用状态或宿主状态。

### 3. 构建与生命周期

VibeFlow 负责：

- 静态检查扩展的 target、依赖和 `provides`；
- 检查扩展不能导入 node、base_lib 私有入口、Python runtime/plugin 或业务 registry；
- 将启用的扩展源码和允许的依赖打入 AOT 产物；
- 排除 planned 和当前 workflow 未引用的扩展；
- 生成显式 `createWorkflowHost()`；
- 按依赖拓扑和声明顺序执行 `start()`；
- 按相反顺序执行 `stop()`；
- 保证 `stop()` 幂等；
- stop 时触发该 host instance 的 AbortSignal，并等待其生命周期任务清理；
- 启动失败时停止已经成功启动的扩展，并保留原始 cause。

`createWorkflowHost()` 返回的 handle 提供本构建对应的 `runWorkflow` 或 `runWorkflowAsync`，并自动合并 Host Extension 提供的 Capability 与调用时显式传入的 Capability。

直接使用底层 `runWorkflow`/`runWorkflowAsync` 并手工注入 Capability 仍然合法，不强制所有宿主使用 Host Extension。

模块 import、`createWorkflowHost()` 本身和 `web-app` 构建均不会自动执行工作流。宿主或应用入口必须显式调用 `start()`、工作流入口和 `stop()`。

### 4. 与 Python Plugin 的关系

Python `RuntimePlugin` 继续只服务 Python 编译期或运行时。JS AOT 继续拒绝直接打包 Python Runtime Plugin。

Host Extension 是经过 Node、base_lib、Capability 和 target 静态依赖检查的目标环境源码。
它与 Python Plugin 共享“项目登记可用资源、workflow 显式引用实际资源、
planned 只参加审查”的配置模型，但保留独立 descriptor、源码 ABI 和生命周期。

## 四、Loop

### 1. 配置语义

| 配置 | 行为 |
| --- | --- |
| 省略 `max_iterations` | 保持默认 `1000` |
| 正整数，无 stop | 精确执行 N 次并正常返回 |
| 正整数，有 stop | stop 先满足则返回；上限先耗尽则保持现有超限错误 |
| `null`，有 stop | 无次数上限，直到 stop 满足 |
| `null`，无 stop | 明确的永久循环 |
| 同时声明两个 stop | `stop_after OR stop_when`，先检查 `stop_after` |

- `max_iterations: null` 本身就是用户对无上限运行的显式确认，不增加 `allow_infinite`。
- `stop_after > max_iterations` 改为 warning，配置仍可执行。
- 负数、零、错误类型和非法条件硬失败，因为它们无法形成有效循环定义。
- 不强制 yield、超时、取消路径、collect 上限或退出条件。
- 永久 loop 及被保守证明必不返回的 nodeset 是合法 flow sink。
- 永久 sink 的后续边保留在图中，并产生非阻断 warning。

### 2. 执行与可观测性

- Python Runtime 使用条件式 `while`；
- JS emitter 为有限或无界配置生成静态循环，不引入浏览器端 VibeFlow 解释器；
- 无界 loop 的内存摘要按稳定路径聚合；
- 完整 trace 继续流式输出，不在内存中无限累计；
- detached task 完成后立即从调用级跟踪集合移除；
- 同步永久忙循环可以合法构建，但必须产生明确 warning，因为它会占用当前线程；
- 使用 suspend receive 的长期循环必须声明 `entry_mode: async`。

Mermaid、ASCII 和 Architecture JSON 显示：

- `max: unbounded`；
- stop 组合；
- loop lifetime；
- completion、schedule 和 executor；
- `io:receive(port)`/`io:send(port)`。

## 五、原生 IO

### 1. 内核节点

新增内核特殊节点：

```jsonc
{
  "id": "receive_request",
  "type_used": "vibeflow.io",
  "provides": [{"key": "request", "type": "app.request"}],
  "io": {"operation": "receive", "port": "requests"}
}
```

```jsonc
{
  "id": "send_response",
  "type_used": "vibeflow.io",
  "requires": [{"type": "app.response", "cardinality": "exactly_one"}],
  "io": {"operation": "send", "port": "responses"}
}
```

- `receive` 必须零输入、一个输出；
- `send` 必须一个 `exactly_one` 输入、零输出；
- 节点自动使用现有 `flow_kind="io"`；
- `port` 必须是非空字符串；
- IO 节点仍是普通流程节点，不隐式充当 terminal start/end。

### 2. `vibeflow.port` 契约

固定两种 operation 的完成语义，不允许同一 operation 在同步与异步之间浮动：

```ts
interface VibeFlowPort {
  // completion: suspend
  receive(
    input: { port: string },
    context: { signal?: AbortSignal },
  ): Promise<{ value: unknown }>;

  // completion: immediate
  send(
    input: { port: string; value: unknown },
    context: { signal?: AbortSignal },
  ): null;
}
```

- JS `receive` 只能用于 `entry_mode: async`；
- JS `send` 表示把值提交给宿主队列或接收端后立即完成；
- 需要远端确认或处理回执的项目必须声明单独的 suspend Capability operation，例如项目自己的 `send_and_wait`，不得重载核心 `send`；
- Python 首版 `receive` 和 `send` provider 都使用同步 callable；
- Python 阻塞式 receive 从调度器角度仍是 immediate callable，不改变 Python 公共入口；
- 普通 JS/TS node 可以显式使用 `vibeflow.port`，但必须声明 `flow_kind="io"`；
- base_lib 仍不得访问 Capability。

长期服务程序由以下结构直接表达：

```text
entry_mode: async
→ max_iterations: null 的 loop
→ receive
→ 普通 Node/Nodeset
→ send
→ 下一次 receive
```

必须立即返回的宿主回调使用 `entry_mode: sync` 的纯同步工作流。状态快照作为普通输入传入；网络、事件和异步存储由异步工作流处理。

## 六、Portable Plan 与构建改造

在现有语言无关计划上增加：

- `WorkflowPlan.entry_mode`；
- implementation/capability operation 的 `completion`；
- 独立 `TaskPlan`；
- `schedule` 与 `executor`；
- `IoPlan`；
- Host Extension descriptor、依赖计划和构建资源。

Python Target 把 `async_mode` 和 `result_key` 编译成明确的 TaskPlan 引用或 schedule 信息，避免路线布尔值承担多种语义。

构建清单记录：

- workflow ABI version；
- entry mode；
- completion/schedule/executor 摘要；
- Host Extension 及其依赖；
- Host Extension 提供的 Capability；
- 无法检查源码的宿主信任边界；
- loop lifetime 和 Port operation。

三个现有 JS AOT profile 均支持新 ABI 和 Host Extension。`single-esm` 仍不得产生隐式本地 companion chunk，`web-app` 仍由用户应用入口显式启动 host。

## 七、诊断规则

新增或调整稳定诊断码：

- `GRAPH.LOOP.UNBOUNDED`；
- `GRAPH.LOOP.NONRETURNING`；
- `GRAPH.LOOP.NONRETURNING_OUTGOING`；
- `AOT.ENTRY_MODE.SUSPEND_IN_SYNC`；
- `AOT.ENTRY_MODE.TASK_IN_SYNC`；
- `AOT.COMPLETION.MISMATCH`；
- `AOT.PROMISE.UNOWNED`；
- `AOT.HOST_EXTENSION.INVALID_DEPENDENCY`；
- `AOT.HOST_EXTENSION.MISSING_CAPABILITY`；
- `AOT.HOST_EXTENSION.LIFECYCLE`。

原则：

- 无法表达、契约自相矛盾或静态声明不真实时硬失败；
- 用户明确声明的永久循环、忙循环和无取消路径只产生 warning；
- 不把代码风格偏好升级成构建护栏；
- 不以运行时猜测替代构建期契约检查。

## 八、实施顺序

1. 为现有 Python、JS AOT、`result_key` 和 detached 行为补齐 characterization/golden tests。
2. 加入 `entry_mode`、`completion`、TaskPlan、executor 模型和 Python Target 转换。
3. 改造 JS emitter，分别生成同步 `runWorkflow` 和异步 `runWorkflowAsync`。
4. 使用 TypeScript Compiler API 实现同步闭包、Promise 所有权和 completion 检查。
5. 实现 Host Extension descriptor、依赖检查、打包和生命周期 helper。
6. 实现无界 loop、双 stop、永久 sink 和对应诊断。
7. 实现 `vibeflow.io`、固定 Port 契约及 Python/JS Capability 接线。
8. 更新 Mermaid、ASCII、Architecture JSON、构建清单和 source map。
9. 更新 JavaScript 与 Python integration Sandbox、开发文档和分发文档。
10. 运行完整测试和两个 Sandbox，再用 `distribution/build.py` 重建并检查分发包。

## 九、测试与验收

### 执行模型

- 默认 JS 工作流返回普通值而不是 Promise；
- 显式异步工作流只导出 `runWorkflowAsync`；
- suspend 实现进入同步工作流时构建失败；
- immediate 声明与 Promise 返回类型不一致时构建失败；
- 不发生同步到异步的自动升级；
- Python 旧同步、result_key 和 detached 配置保持原行为；
- import 模块不会产生业务副作用。

### TaskPlan 与静态审计

- inline suspend 保持串行，不产生伪分支；
- deferred 结果只在显式 result_key join 时进入主流程；
- detached 任务属于单次调用并正确清理；
- 隐藏 `.then()`、`void promise`、模块级 Promise 和 node 内监听器被拒绝；
- 两次调用的 context、trace、任务和错误互不污染。

### Host Extension

- 每个 host handle 使用独立 extension instance；
- start 按顺序、stop 按反序执行；
- stop 可重复调用；
- 部分 start 失败时已启动扩展得到清理；
- Capability 自动注入对应 host handle 的工作流调用；
- 手工调用底层 workflow ABI 仍可使用 fake Capability；
- 构建产物 import 和 `createWorkflowHost()` 都不会自动 start。

### Loop 与 IO

- 覆盖有限无 stop、`null + stop_after`、`null + stop_when`、双 stop OR、超限失败、永久 loop 和嵌套永久 nodeset；
- 永久 sink 的下游只产生 warning，review 仍可成功；
- `receive -> 数学 node/base_lib -> send` 在 Python 和 JavaScript integration Sandbox 中得到一致结果；
- async receive、immediate send、缺失 operation、Schema 错误和 AbortSignal 行为正确；
- 长期 loop 的 trace 和任务集合不随迭代次数无界增长；
- 同步快照工作流可在普通同步回调中直接返回结果；
- Node/browser target 和三个 AOT profile 均通过；
- wheel 与开发分发包包含 descriptor、Schema、Host Extension 构建资源和更新后的文档。

## 十、边界

VibeFlow core 提供 WorkflowPlan、TaskPlan、Host Extension 生命周期和 Port
契约。项目通过 Host Extension 实现具体队列、宿主事件、receipt、背压和服务接线。
Web Worker executor、第三方宿主源码的运行时 Promise 检测，以及
`io`、`document`、`data_store` flow kind 重构属于后续独立改造。
