# Workflow 异常处理与资源收尾：未来开发计划

状态：待设计、未实施。决策日期：2026-10-21。本文件登记未来能力，不表示当前版本已经提供这些保证，也不把尚未设计的全框架异常处理列为方案 B 的迁移缺陷。

## 目标与范围

让 workflow 在正常结束、节点报错和用户取消时，对已建立的资源有明确的收尾责任，并使用户能知道原始失败发生在哪里、收尾是否成功。统一考虑 Python / JavaScript、源码 / AOT 和浏览器宿主，沿用现有编译与执行链路。

例如：浏览器 workflow 先建立消息监听，收到消息后执行处理节点，最后关闭监听。正常路径能走到关闭节点；处理节点报错时，普通顺序连线本身不能保证关闭节点仍被执行。目前浏览器会话包装层还有 abort 收尾行为，但这不等于框架已有统一的异常路径语义。

需要收尾的对象包括消息监听、待接收消息的等待者、定时器及本次运行建立的连接；具体对象以实际适配器为准。关闭只针对本次运行拥有的资源，共享宿主对象不能随单个 workflow 任意销毁。

## 当前起点与证据边界

- `sandbox/javascript/integration/project/nodes/session_lifecycle.ts` 用普通节点表达建立与关闭；`configs/browser_message_loop.jsonc` 表达正常业务流程。
- `sandbox/javascript/integration/project/web/browser_session.ts` 在会话结束或停止时触发 abort；`adapters/window_ports.ts` 响应 abort 并关闭监听。这是当前实际路径，不能因为未来要统一就先删掉。
- 审核中的 Node AOT 能力替身实验：建立资源后注入错误，仅观察到 open，未观察到 close。它说明普通图的末尾关闭节点不足以覆盖异常；不证明浏览器包装层实际泄漏。
- `tests/tooling/test_explicit_lifecycle.py` 中通过宿主包装层的取消或错误用例，不能单独证明所有 Target、所有入口具有同样的资源收尾保证。

## 开发阶段

1. **定义可观察语义。** 盘点现有错误传播、取消、并发分支停止与宿主关闭行为。明确正常结束、失败、取消各自的结果；区分“已提出取消”与“资源已关闭”。先写场景与预期，再定接口。
2. **确定责任归属与图中表达。** 设计资源建立成功后如何登记归属、如何表达异常/取消时的收尾，以及谁负责触发。关键生命周期行为应可审查，不恢复 Host Extension 或形成宿主与 workflow 两套竞争的业务执行路径。具体采用图内异常结构还是执行器支持的显式收尾结构，留到原型验证后定型。
3. **做最小两端原型。** 用“建立监听 → 接收一条消息 → 处理失败 → 收尾”贯通 Python 与 JavaScript 的源码和 AOT；再接入真实浏览器。复用现有执行器，不引入另一个执行框架。
4. **覆盖复杂控制流。** 处理建立到一半失败、嵌套 Nodeset / Loop、并发分支仍在工作、重复停止、接收等待中取消及收尾自身失败。明确收尾顺序和重复调用语义，避免以未证明的“恰好一次”掩盖中断风险。
5. **统一入口并替换旧职责。** 新机制覆盖现有宿主行为并通过验收后，迁移调用和删除被替代的收尾路径。底层适配器仍可提供关闭 API，但不应隐式决定业务流程。同步 ABI、SDK、诊断、用户文档和发行案例。

自动重试、事务回滚、断点恢复、进程崩溃后的持久恢复不自动纳入本计划；如有必要应另行确认需求。进程被强制终止或浏览器崩溃时，也不能承诺普通 workflow 仍能执行收尾代码。

## 验收场景

| 场景 | 应验证的最终表现 |
| --- | --- |
| 正常完成 | 本次运行的监听、等待者与连接按约定释放，结果可用 |
| 处理节点失败 | 原始错误可定位，已建立资源按约定收尾，不再收到该次运行的业务消息 |
| 等待消息时取消 | 等待结束，取消状态和收尾状态可区分，下一次运行不重复接收 |
| 建立过程部分失败 | 已获得的部分资源有明确负责人，未获得的资源不被误关闭 |
| 重复停止或并发结束 | 不重复触发业务副作用，不关闭其他运行拥有的资源 |
| 收尾本身失败 | 保留原始错误，同时报告收尾失败，不能静默覆盖任一结果 |
| 嵌套及并发 | 父子资源归属、分支终止与收尾顺序符合已确定语义 |
| 源码与离线 AOT | 相同场景的结果一致，AOT 不新增项目扫描与审图 |

以实际资源状态和用户可见行为验收；真实浏览器需测试重复启动、消息接收、取消、错误及关闭后的消息不再进入旧运行。能力替身可用于故障注入，但不能代替真实宿主验证。复用现有沙箱，不为此建设独立测试框架。

## 执行中的成本、目标与路线复核

关键假设是现有执行器可以承载统一异常与收尾语义，普通节点及明确的控制结构足以表达资源责任，宿主只需提供能力 API。这些是假设，尚未完成设计证明。主要成本在两端执行语义、并发取消、ABI 迁移与真实浏览器验证；精确工时未知，应以最小原型测量剩余实现、验证和迁移成本，同时评估是否减少后续维护中的重复职责。

在首个两端源码/AOT原型、首个真实浏览器错误与取消验收、并发收尾语义验证，以及删除现有宿主路径前复核目标和假设。出现连续补偿逻辑时提前复核，复用已有证据，不额外逐项审批。

按 `critical-fork` 自主处理等价实现。如果证据要求改变图中可审查的生命周期承诺、取消效果或资源责任，先做低成本核查，再用可独立阅读的中文说明同一场景下各路线的机制、结果、代价和未知，请用户判断。可保留的选项明确下一讨论节点，最迟定型前讨论；只暂停依赖决定的部分，继续独立工作。确需介入时先完整说明，再按 `codex-task-alert` 的资格规则提醒；决定后更新本计划、验收依据和决策记录。完成通知同样遵循该 skill 的资格规则。

实施完成后，将持续有效的语义纳入当前设计和用户手册，删除本计划的退役内容，不转入历史归档。相关现有清理工作见[项目准备规范](../maintainers/project-preparation.md)。
